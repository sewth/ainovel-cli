# 新书底盘工作流说明 v1

这份文档是给我们自己后续开新书用的。

目标很简单：

- 不要每次都从零试错
- 不要每次正文跑偏了才临时补 prompt
- 尽量把“纠偏”提前到 `foundation` 阶段

---

## 一、推荐工作流

### 第 1 步：先定底盘，不急着写正文

先复制这份模板：

- [新书底盘填写模板-v1.md](/Users/jieyuqing/document/ainovel-cli/docs/模板/新书底盘填写模板-v1.md)

优先填这些：

1. 书名
2. 一句话卖点
3. 核心玩法
4. 风格口径
5. 主角底盘
6. 世界观底层逻辑
7. 系统本质
8. 长线主轴
9. 第一章必须做到什么
10. 前 5 章目标

不要一开始就追求“填得最全”，先保证不会写歪。

---

### 第 2 步：生成或手工整理 foundation

有两种做法：

1. 你自己已经想得比较清楚

直接手填或半手填 `premise / characters / world_rules / outline / compass`

2. 你只想好了核心方向

把模板内容喂给规划层，让它帮你补齐 foundation

建议原则：

- 规划层负责“补细化”
- 不是负责“改方向”

---

### 第 3 步：foundation 落盘后先备份

建议每次 foundation 进入“可写正文”状态后，都做一次备份。

推荐做法：

1. 打一个压缩包
2. 保留一份“初始可用版”
3. 后面每次大改前再备份一次

这样如果某轮修改把底盘带歪了，可以直接回滚，不用一点点救。

---

### 第 4 步：写正文时只给短 prompt

写正文尽量不要反复塞整套大底盘。

推荐分工：

- `foundation` 负责长期稳定方向
- `短写稿 prompt` 只负责当前阶段

比如：

- 开篇阶段只控制“第一章要有生活感和异常感”
- 中段阶段只控制“灰产升级别写成纯打架”

不要把底盘、风格、长线、卷纲、当前章节要求全部糊到一个 prompt 里。

---

## 二、什么时候优先改 foundation

遇到下面这些问题，优先改 `foundation`，不要只改章节 prompt：

1. 主角反复自我介绍职业背景
2. 开篇总是写成说明书
3. 模型总爱提前解释世界观
4. 每一章都像在赶 KPI
5. 配角功能太工具化
6. 长线提早抖完
7. 后期总想往战力升级上跑

因为这些通常不是“单章写歪”，而是底盘本身给了错误暗示。

---

## 三、什么时候只改短写稿 prompt

下面这些情况，更适合先改短 prompt：

1. 第一章异常出现太晚
2. 最近几章节奏拖了
3. 某一小段写得解释太多
4. 某一卷的起手不够抓人
5. 当前阶段的钩子不够强

这种更像“阶段性写法问题”，不一定要动整套底盘。

---

## 四、推荐维护顺序

如果正文出问题，建议按这个顺序检查：

1. 先看 `foundation` 有没有写死错误方向
2. 再看短写稿 prompt 是否阶段目标太多
3. 再看当前生成结果是不是单次发挥失常

不要一上来就不断往章节 prompt 里补条款。

否则很容易变成：

- prompt 越补越长
- writer 越写越缩
- 章节越写越像任务清单

---

## 五、建议长期保存的 foundation 文件

如果后面我们把流程固定下来，推荐每本书都至少保留这些：

1. `premise.md`
2. `characters.md` / `characters.json`
3. `world_rules.md` / `world_rules.json`
4. `outline.md`
5. `layered_outline.md`
6. `meta/compass.json`
7. `meta/progress.json`

说明：

- `premise` 管总方向
- `characters` 管人设底盘
- `world_rules` 管世界和系统边界
- `outline` / `layered_outline` 管节奏和卷弧
- `compass` 管终局方向和风格锚点
- `progress` 容易影响模型对篇幅和节奏的默认判断

---

## 六、开新书的最低可用流程

如果想最快开一本新书，可以用这个最简流程：

1. 复制 [新书底盘填写模板-v1.md](/Users/jieyuqing/document/ainovel-cli/docs/模板/新书底盘填写模板-v1.md)
2. 先填最核心的 10 项
3. 让规划层补齐 foundation
4. 检查开篇、主角、人设、风格有没有写死
5. 备份 foundation
6. 用短写稿 prompt 开写前 5 章
7. 如果正文跑偏，先改 foundation，再重新写

---

## 七、目前这套流程的经验总结

我们这次已经验证出几个比较重要的经验：

1. 大而全的写稿 prompt，不一定比短 prompt 好用。
2. 长篇底盘和短写稿要求，最好分开。
3. 风格口径最好写进底盘，不要只写进前几章 prompt。
4. 如果 `progress` 之类的元数据把章节数压太死，模型真的可能会压剧情。
5. 正文跑偏时，改 foundation 往往比继续补章节 prompt 更有效。
